# Exercise 08 — SPI

## Metadata
- **Mode:** SIM → BOARD
- **Level:** 2 Intermediate
- **Primary language phase:** ASM → C
- **Hardware:** EduBoard-AVR or STK500; SPI peripheral for Q2
- **Qualification:** Q1 + Q2
- **Concepts:** SPI, clock divider, controller mode, SPCR, SPSR, SPDR

## Learning objectives
Explain synchronous serial transfer, identify SCK/MOSI/MISO/SS roles, calculate SPI clock and follow one byte from CPU register to bus transfer and back.

## Mental model
```text
controller                 peripheral
SPDR -> shift register -> MOSI -------->
        clock generator -> SCK -------->
                         <- MISO <- shift register
SS ------------------------ select ----->
```

## Short theory
SPI shifts bits in both directions while the controller supplies a clock. Configuration determines role, clock rate and sampling behavior. A byte written by software starts peripheral hardware activity.

## Part A — Assembly / Q1
Configure controller mode, GPIO directions and an F_CPU/16 clock. Write a byte to SPDR, wait for completion and read the received byte.

Calculate the clock frequency before running.

## Observe
Inspect DDRB, SPCR, SPSR and SPDR. Identify which software action starts a transfer and which status indicates completion.

## Part B — C / Q1
Implement the same transfer in register-level C. Disassemble the transfer loop and compare it with assembly.

## Under the hood
```text
C transfer(byte) -> SPDR write -> SPI shift hardware -> pins
                 -> completion flag -> SPDR read -> C return value
```

## Part C — Board / Q2
Connect a known SPI peripheral or loopback arrangement appropriate to the lab. Observe SCK/MOSI/SS with a logic analyzer where available and verify transferred data.

## Task
Change the clock divider, predict the new SCK frequency and verify the configuration before Q2 measurement.

## Expected result
A transfer starts from a data-register write and completes under peripheral hardware control; measured Q2 clock should agree with the configured clock within hardware tolerances.

## Questions
- Why is SPI called synchronous?
- Why is SCK generated by the controller?
- Why is SS important even with one peripheral?
- Can software know the physical signal integrity from SPCR alone?
- What part of the transfer continues without CPU bit-banging?

## Challenge
Design a small reusable `spi_transfer` routine and use it to send a multi-byte command sequence.

## Qualification boundary
Q1 covers configuration and modeled peripheral behavior. Q2 covers real SCK/MOSI/MISO/SS signaling and external-device communication.
